# 공지사항 관리 시스템 전략 (Notice Management Strategy)

현재 사용 중인 `JSON 파일 방식`의 장단점과, 향후 업그레이드할 수 있는 대안들을 정리했습니다.

## 1. 현재 방식: GitOps (JSON/Static)
소스 코드 안에 공지사항 데이터(`public/notices/*.json`)를 포함시키고, Git으로 버전을 관리하는 방식입니다.

### 장점 (Pros)
*   **CI/CD와 찰떡궁합**: 글을 수정하고 `git push`만 하면 파이프라인이 자동으로 배포해주므로, 별도의 관리자 페이지가 필요 없습니다.
*   **비용 0원**: DB 조회 비용이 들지 않고, S3/CloudFront가 캐싱해서 엄청나게 빠릅니다.
*   **버전 관리**: 누가 언제 공지사항을 바꿨는지 Git 히스토리에 다 남습니다. (되돌리기 쉬움)
*   **개발자 친화적**: 에디터에서 바로 수정 가능.

### 단점 (Cons)
*   **비개발자 수정 불가**: 마케터나 운영자가 공지를 쓰려면 Git을 배워야 합니다.
*   **재배포 필요**: 오타 하나 고쳐도 전체 사이트 빌드/배포 과정(약 2분)을 거쳐야 합니다.

---

## 2. 발전된 방식: Serverless DB (DynamoDB + Lambda)
공지사항 데이터를 코드에서 분리하여 AWS DynamoDB에 저장하고, API로 불러오는 방식입니다. '랭킹 시스템'과 같은 구조입니다.

### 장점 (Pros)
*   **실시간 반영**: DB만 고치면 즉시 반영됩니다. (재배포 불필요)
*   **관리자 페이지 개발 가능**: 운영팀을 위한 "공지사항 글쓰기" 페이지를 만들 수 있습니다.
*   **유연성**: 조회수 카운트, 댓글 기능 등을 붙이기 쉽습니다.

### 단점 (Cons)
*   **개발 공수**: CRUD API(작성, 수정, 삭제)와 프론트엔드 연동을 모두 개발해야 합니다.
*   **비용/속도**: JSON 보다는 미세하게 느릴 수 있습니다(API 호출 시간).

---

## 3. 추천 전략 (Recommendation)

### 1단계: 현재 방식 유지 (GitOps) ✅
**"지금 파이프라인이 너무 잘 되어 있어서 가장 추천합니다!"**
*   혼자 개발하고 운영하신다면, 굳이 관리자 페이지를 만들 시간에 **게임 기능(컨텐츠) 개발**에 집중하는 게 효율적입니다.
*   `JSON` 파일 형식이 불편하다면, 내용을 `Markdown(.md)` 파일로 관리하고 프론트에서 렌더링하도록 바꾸는 정도만 업그레이드해도 충분합니다.

### 2단계: Markdown 도입 (옵션)
*   긴 글을 JSON의 `\n` 으로 쓰는 건 힘듭니다.
*   `react-markdown` 라이브러리를 설치하고, 공지 내용을 `.md` 파일로 분리하면 글쓰기가 훨씬 편해집니다.

### 3단계: 나중에 팀이 커지면 (DB 도입)
*   비개발자 운영팀이 생기면 그때 DynamoDB + Admin Page를 만드시는 것을 추천합니다.
