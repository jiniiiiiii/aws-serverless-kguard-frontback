# ECS Pihagi Game 단일 컨테이너 부하 테스트 결과 분석

# 테스트 1
## 1. 개요
*   **목적**: ECS Fargate에서 실행 중인 `pihagi` 단일 컨테이너의 최대 동시 접속 수용량(Capacity) 파악
*   **테스트 환경**: t3.small (추정) / Node.js Single Thread
*   **부하 조건**: 요청 1건당 CPU를 강제로 5초간 점유 (`duration=5000`)

---

## 2. 구간별 상세 분석

### A. 안정 구간 (Stable)
*   **동시 접속자**: 약 30명
*   **상태**: **매우 안정적**
*   **근거 데이터 (`intermediate` 로그 2~123행)**:
    ```json
    "http.responses": 58,
    "http.codes.200": 9,
    "vusers.active": 31,
    "errors.ETIMEDOUT": 0
    ```
    *   에러가 전혀 발생하지 않았으며, 평균 응답 시간도 약 5.9초로(로직 수행 5초 + 대기 0.9초) 정상 범위입니다.

### B. 임계점 (Breaking Point)
*   **동시 접속자**: 약 40~45명
*   **상태**: **불안정 시작 (초기 장애 발생)**
*   **근거 데이터 (`intermediate` 로그 124~261행)**:
    ```json
    "vusers.created": 50,
    "vusers.active": 45,
    "plugins.metrics-by-endpoint./api/stress-cpu.errors.ETIMEDOUT": 8,
    "errors.ETIMEDOUT": 8
    ```
    *   동시 접속자가 40명을 넘어가면서부터 **타임아웃(ETIMEDOUT)이 8건 발생**했습니다.
    *   CPU 처리가 밀리기 시작하여 요청이 대기열에서 만료되기 시작한 시점입니다.

### C. 과부하 구간 (Overload)
*   **동시 접속자**: 50명 (최대)
*   **상태**: **서비스 장애 (Service Degradation)**
*   **근거 데이터 (`intermediate` 로그 262행 이후)**:
    ```json
    "vusers.active": 50,
    "plugins.metrics-by-endpoint./api/stress-cpu.errors.ETIMEDOUT": 27,
    "errors.ETIMEDOUT": 27,
    "http.response_time.2xx.mean": 8970.9
    ```
    *   **타임아웃이 27건**으로 급증했습니다. (요청의 절반 이상 실패)
    *   성공한 요청조차 응답 시간이 평소보다 3초 이상 지연된 **약 9초**(`8970ms`)가 소요되었습니다.

---

## 3. 결론
1.  **적정 수용량**: 단일 컨테이너 기준 **동시 접속자 30~35명**
2.  **한계 원인**: 
    *   Node.js의 싱글 스레드 특성상 CPU 부하 작업(5초 루프)이 들어오면 이벤트 루프가 차단됨.
    *   35명 이상의 요청이 들어오면 대기 큐(Backlog)가 가득 차거나 타임아웃 발생.
3.  **제언**:
    *   **Auto Scaling 정책**: CPU 사용률 50% 도달 시 즉시 스케일 아웃하도록 설정 필요.
    *   **Graceful Degradation**: 40명 이상 접속 시 대기열 안내 메시지 표시 고려.
    *   **Scale-out Lag (중요)**: 이번 테스트 실패의 주 원인 중 하나는 **오토스케일링이 반응하기 전(약 1~3분 소요)에 트래픽이 급증했기 때문**입니다. 스케일 아웃이 완료될 때까지 단일 컨테이너가 버티지 못했습니다. (Warm-up 시간을 늘려야 함)

# 테스트 2 (Auto Scaling 검증 결과)
## 1. 개요
*   **실행 시간**: 11:44경 오토스케일링(Scale-out) 관측됨
*   **결과**: **실패 (Death Spiral 현상 발생)**
*   **현상 요약**: 오토스케일링이 동작했으나, 이미 단일 태스크가 처리 불가 상태(Backlog)에 빠진 상태에서 트래픽이 추가로 증가하여 시스템이 회복하지 못함.

## 2. 상세 분석

### A. Phase 1 (0~5분): 단일 태스크 과부하 및 지연된 스케일링
*   **설정**: Arrival Rate 5명/sec (기대 동시접속자 25명)
*   **실제 상황**:
    *   응답 시간이 5초를 넘어 8초~타임아웃(10초)까지 지연됨.
    *   이로 인해 동시 접속자(`vusers.active`)가 기대치(25명)의 두 배인 **50명**까지 누적됨.
    *   이미 1개의 태스크는 **처리 한계(35명)**를 초과하여 타임아웃을 쏟아내고 있었음.
*   **Scaling Event (11:44)**:
    *   테스트 시작 약 4~5분 경과 시점에 CPU 부하를 감지하고 태스크가 3개로 늘어남.
    *   잠시 부하(CPU/Memory)가 줄어드는 듯 했으나, **이미 쌓여있는 대기열(Backlog)**을 처리하기에도 벅찬 상태.

### B. Phase 2 & 3 (5분 이후): 죽음의 소용돌이 (Death Spiral)
*   **설정**: Arrival Rate 20명/sec (기대 동시접속자 100명)
*   **실제 상황**:
    *   태스크가 3개로 늘어나서 이론상 **105명**(35명 * 3)까지 처리가 가능한 시점.
    *   하지만 이미 Phase 1의 실패한 요청들이 시스템을 잡고 있는 상태에서, 신규 트래픽이 쏟아짐.
    *   응답 속도가 느리니 접속 유지 시간이 길어지고, 순식간에 **동시 접속자가 200명**(`vusers.active`)을 돌파.
    *   이는 3개 태스크의 한계(105명)를 **200% 초과**한 수치.
    *   결국 모든 요청이 **Timeout(100% 에러)**으로 끝남.

## 3. 결론 및 교훈
1.  **Backlog의 무서움**: 오토스케일링이 되더라도, 이미 쌓인 요청 처리에 허덕이면 새로운 트래픽을 감당하지 못합니다.
2.  **임계치 설정**: `Phase 1` 부하가 너무 강했습니다. (25명 기대했으나 50명 누적됨). 오토스케일링 트리거용 부하는 처리 한계(30명)보다 **약간만 높게(32~35명)** 잡아야 안전하게 스케일 아웃 테스트가 가능합니다.
3.  **운영 제언**: 실제 라이브 서비스에서도 "부하가 꽉 찼을 때" 스케일 아웃하면 늦습니다. **부하가 50~60% 일 때 미리 늘어나도록** 민감하게 설정해야 합니다.

## 4. 최적화 전략 (Action Plan)
*   **문제**: 현재 단일 태스크 한계(30명)와 오토스케일링 지연(3분) 사이의 간극
*   **해결책**: **CPU 임계치 하향 조정 (60% -> 40~45%)**
*   **기대 효과**:
    *   동시 접속 **15~20명** 수준(서버 부하 여유 구간)에서 조기 확장(Scale-out) 시작
    *   3분 후 트래픽이 30명에 도달할 시점에는 **이미 새 태스크가 준비 완료**됨
    *   'Death Spiral' 없이 매끄러운 트래픽 분산 가능

# 테스트 3 (최종: 임계치 조정 후 검증)
## 1. 개요
*   **변경 사항**: Auto Scaling CPU 임계치 하향 조정 (60% -> 40~45% 추정)
*   **결과**: **대성공 (Very Stable)**
*   **현상 요약**: 초기부터 안정적인 응답 속도를 유지하며, 스케일링이 적절히 이루어져 트래픽 증가에도 서비스가 흔들리지 않음.

## 2. 상세 분석

### A. Phase 1 (Warm-up & Scale-out Trigger)
*   **동시 접속자**: 약 30명 유지
*   **상태**:
    *   `errors.ETIMEDOUT`: **0건** (완벽)
    *   평균 응답 시간: **약 5.7초** (매우 안정적)
    *   이전 테스트와 달리 초기부터 에러 없이 깔끔하게 처리함. 낮은 임계치 덕분에 서버가 여유를 가지고 트래픽을 처리함.

### B. Phase 2 & 3 (Ramp-up & Sustained Load)
*   **동시 접속자**: 최대 120명 이상 도달 (예측)
*   **상태**:
    *   트래픽이 늘어나도 응답 시간이 5초 후반~6초 초반대로 일정하게 유지됨.
    *   **Scale-out이 제때 발동**하여(선제적 대응), 단일 태스크가 과부하(Backlog)에 빠지지 않고 새 태스크들과 부하를 잘 나눠가짐.
    *   **Death Spiral** 현상이 완전히 사라짐.

### C. 증거 데이터 (Evidence)
**1. 에러율 0% (Zero Timeouts)**
부하가 최대로 치닫는 시점(Phase 3)에서도 `ETIMEDOUT`이 전혀 발생하지 않았습니다.
```json
// ecs부하테스트-조정후_최종.json (Line 1030~)
"counters": {
  "http.codes.200": 48,
  "vusers.failed": 0,           // 실패 0
  "errors.ETIMEDOUT": 0,        // 타임아웃 0 (Json에 키 자체가 없음)
  "vusers.completed": 48,
  "vusers.active": 30
}
```

**2. 안정적인 응답 속도 (Stable Latency)**
트래픽이 증가해도 응답 시간(p95)이 6.4초 내외로 방어되었습니다. (Test 1 때는 10초 초과)
```json
// ecs부하테스트-조정후_최종.json (Summary)
"http.response_time": {
  "min": 5070,
  "max": 7337,
  "mean": 5862.1,
  "p50": 5826.9,
  "p95": 6439.7,   // 95%의 요청이 6.4초 이내 처리됨 (매우 안정적)
  "p99": 6702.6
}
```

## 3. 최종 결론
1.  **설정 유효성 입증**: "CPU 40~45% 임계치" 전략이 효과적임이 증명됨.
2.  **서비스 안정성 확보**: 이제 급격한 트래픽 증가(Death Valley 구간)를 버틸 수 있는 내성을 갖춤.
3.  **운영 가이드**: 향후 트래픽 패턴이 바뀌더라도 **"Scale-out Lag(3분)를 고려하여 임계치를 낮게 잡는 원칙"**을 고수하면 안정적인 서비스가 가능함.
