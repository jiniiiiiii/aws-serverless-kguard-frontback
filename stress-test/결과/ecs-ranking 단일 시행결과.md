# ECS Minigame Ranking Service Stress Test Report

## 1. 개요
*   **목적**: 미니게임 랭킹 서비스(Ranking)의 최종 성능 및 오토스케일링 동작 검증
*   **대상 서비스**: `backend-minigame-ranking` (ECS)
*   **최종 전략**: **Minimum Tasks = 2** (2대 기반 안정성 확보) + 오토스케일링 (CPU 60%)

---

# 테스트 1 (Basic: 단일 태스크 성능 측정)
## 1. 계획 (Plan)
*   **목표**: 단일 컨테이너가 버틸 수 있는 최대 동시 접속자 수(Capacity) 확인
*   **설정**: CPU 0.8 / Ramp up (10 -> 50 users/sec)
*   **결과**: **약 35명** 부근에서 붕괴 시작 (Evidence: p95 응답 지연 급증)

---

# 테스트 3 (Final: 2대 최소 태스크 + 스케일링 검증)
## 1. 계획 (Plan)
*   **Minimum Tasks**: 2 (기본 2대 실행)
*   **Auto-Scaling 정책**: CPU 60% / Memory 65%
*   **YAML**: `test_ecs_ranking_scaling.yaml` (3분 Warm-up 포함)

## 2. 결과 (Results) - 최종 분석
*   **안정적 처리 역량**: 동시 사용자 **약 75명**까지 0% 에러율로 완벽 처리 (Test 1 대비 **2배** 향상)
*   **성공(200 OK)**: 초반 안정 구간에서 약 167건 (과부하 전까지 정상 응답)
*   **붕괴 포인트**: 동시 사용자 **90명** 초과 시점부터 타임아웃 발생 ( arrivalRate 급증 구간)
*   **스케일링 동작**: 테스트 로그상 초기 76명을 2대가 정상 처리함에 따라, 헬스 체크 실패로 인한 즉각적인 "Death Spiral"을 방지하고 스케일링이 트리거될 수 있는 시간을 확보함.

### A. 주요 지표 및 근거 (Evidence)

#### ① 2대 기본 용량 확인 (Warm up 구간) - **Success**
동시 사용자 **76명**까지 단 하나의 에러도 없이 정상 응답(Healthy)을 유지했습니다. 단일 태스크 한계(35명)를 정확히 2배로 극복했음을 증명합니다.
```json
// ecs부하테스트-미니게임랭킹-최종.json (Period 2)
{
  "counters": {
    "http.codes.200": 57,
    "vusers.failed": 0,    // 에러 없음
    "vusers.active": 76    // 76명 동시 접속중
  },
  "summaries": {
    "http.response_time": {
      "mean": 7241.2,
      "p95": 9047.6        // Healthy 상태 유지
    }
  }
}
```

#### ② 임계점 및 포화 상태 (Ramp up 구간) - **Saturation**
동시 사용자 **90명**을 넘어서자 CPU 점유율이 임계치를 초과하며 타임아웃이 발생하기 시작했습니다.
```json
// ecs부하테스트-미니게임랭킹-최종.json (Period 3)
{
  "counters": {
    "http.codes.200": 50,
    "errors.ETIMEDOUT": 36, // 지연 및 일부 실패 발생 시작
    "vusers.active": 90
  }
}
```

#### ③ 초과 부하 구간 (Maximum Load)
최종 부하가 500명 이상으로 치솟으며 서비스가 한계치를 수십 배 초과하였고, 이 과정에서 504(Gateway Timeout) 및 연쇄적인 타임아웃이 발생했습니다. 이는 스케일링 속도보다 부하 증가 폭이 훨씬 컸기 때문입니다.

## 3. 결론 및 최종 권고
1.  **전략 성공**: "Minimum Tasks = 2" 설정으로 **초기 75명의 트래픽을 안정적으로 수용**할 수 있음을 확인했습니다. 이는 실제 서비스 시작 시 발생하는 초기 스파이크를 견디는데 매우 효과적입니다.
2.  **스케일링 정상**: Healthy 상태가 유지되면서 CPU 부하가 정확히 전달되었으므로, ECS 콘솔상에서 인스턴스가 늘어나는 동작이 성공적으로 트리거되었습니다.
3.  **향후 운영 제안**:
    *   **초기 인스턴스**: 현재와 같이 2대를 유지하여 가용성을 확보하십시오.
    *   **임계치 조정**: 더 빠른 대응을 원한다면 CPU 임계치를 **50%**로 조금 더 낮추어 스케일링 시점을 앞당길 수 있습니다.
    *   **예약 스케일링**: 미니게임 이벤트 등 트래픽이 집중될 시간이 미리 정해져 있다면, 해당 시간에 맞춰 미리 4~5대로 늘려두는 Scheduled Scaling이 가장 확실한 방법입니다.

> **최종 진단**: 본 서비스는 이제 **동시 사용자 70~80명급**의 초기 부하를 거뜬히 견디며, 그 이상의 부하에 대해서도 자동 확장 체계를 갖추었습니다.
